# How work is claimed

The queue is GitHub Issues on the repository. The board is the file STATE.md on the branch `board`, rendered from the issues, the branches, the claim files, the pull requests and, for each open epic and goal, GitHub's sub-issues and blocked-by relations by the board workflow (`python3 -m sdlc_protocol board`, whose rules are sdlc_protocol.board), which rewrites that branch's one commit on every issue and pull request event, every branch made or deleted, every push to the default branch, and every six hours as a fallback; nobody edits it by hand. Read it with `git fetch origin +refs/heads/board:refs/remotes/origin/board && git show origin/board:STATE.md`, which names the branch it writes, since `git fetch origin board` updates no remote-tracking branch in a clone made for one branch, as a cloud session's is; a repository that follows this protocol also prints it from its session-start hook, so every session begins with it. A claim is the first push of a branch: GitHub refuses the second push of the same name, so two workers can never hold the same issue. Everything below is done by the worker doing the work, in the open, and the claim skill that ships with the template and with the symphony plugin is the same steps as commands.

## Workers

A worker is anything that claims issues: a person's sessions, local or in the cloud, with whatever helpers they start; a routine on someone's Claude account, which runs on its own; or runs in GitHub Actions on the repository's own Claude token. There is one way of working for all of them, whether one person works alone, one person runs several sessions and routines at once, or many people and their routines share the repository: each worker claims, works and finishes by the steps below, and the board and the coordinator treat them alike.

Each worker has a name, unique in the repository: its label is `worker:<name>` and its claim files say `- Worker: <name>`, so two workers on one Claude account still tell their claims apart. A person's sessions take the person's GitHub login as their name, unless the session is given another. A routine or a worker in Actions is registered by a small file, `.github/symphony/workers/<name>.json`, which says where it runs (`actions`, `routine` or `session`), what it is for, the area of the repository it prefers (paths or globs), how its pull requests land (`owner`, the repository's owner merges, or `auto-merge`, GitHub merges once the required check is green), and, for a worker in Actions, the model, the turns one run may take and how many runs it may take in a row; it never holds a credential. sdlc_protocol.workers reads and checks those files, and `python3 -m sdlc_protocol workers check` fails on any file that does not hold together. A person may register too, to give their sessions an area. Name a routine or a worker in Actions after its job, not after anyone's login, so it never shares a name with a person's sessions.

## Labels

- todo: the queue. An issue labelled todo and shown unclaimed on the board is free to take as Pick says.
- claimed: a worker has pushed its branch. The worker's own label goes on with it.
- in-review: the pull request is ready; the owner merges it and the merge closes the issue. The claim's labels, this one, claimed and the worker's, stay on the issue the merge closes; once the issue is reopened, the coordinator takes them off, putting todo on as a release does, or takes in-review alone off while a branch stands for it, unless a pull request marked ready from its claim branch finishes the claim (Finish).
- blocker: the issue stops everyone: work it stands in the way of waits until it is done (Blockers).
- worker:<name>: the worker that holds the issue, or that the coordinator gave it before any claim. An issue a worker's label names is that worker's alone: it is left out of the board's Queue and shown under Given to workers until the worker claims it. Where the labels of several workers name one issue, it is theirs alone in the same way: given to each of them, and held by the first of them to claim it, whose Announce takes the others' labels off. The older spellings account:<name> and agent:<name> are read as the same label.
- epic: a request the coordinator plans into tasks (Planning, below). The board's Queue leaves an epic out, since nobody takes one whole.
- goal: a request a person breaks into epics, each an issue labelled epic and a sub-issue of the goal, which the coordinator then plans; the board's Queue leaves a goal out as it leaves an epic out, and its Dependencies section draws each goal above its epics. Only a person puts it on, and the coordinator plans nothing from it: an issue labelled goal is dealt to nobody and listed in no Queue, so a repository whose label goal already means something else renames that label before it takes this protocol.
- blocked: a worker waits on a peer or the coordinator.
- p1, p2, p3: an issue's priority within the place Pick takes it from: one labelled p1 is taken first, then p2, then p3, then an issue with none of them (Pick). A person puts one on, as a control panel's queue does with its arrows; where an issue carries several, the highest counts, and GitHub reads a label's name whatever its case, so P1 is p1.

sdlc_protocol.labels spells these names and the prefixes once, with the colour and description of every label a repository makes up front, every label above but worker:<name>, goal and the priorities; a worker's label is made when the worker first needs it, and goal and a priority are made on the repository's labels page by the person who first needs them, or a priority by the control panel that first puts it on.

## Pick

Fetch, then read the board (`git fetch origin +refs/heads/board:refs/remotes/origin/board && git show origin/board:STATE.md`). Take an issue the Given to workers section gives you first. Else take a blocker, with or without todo, that the Blockers section lists, that nobody has claimed and that no worker's label gives to another, since a blocker comes before the Queue. Else take an open issue labelled todo that the Queue section shows as unclaimed and that no open blocker stands in the way of. Within each of these places take the issues in priority order: one labelled p1 first, then p2, then p3, then one with none of them, the lower number first among equals; the board lists each place in that order, so the first row you may take is the one to take. Of the blockers and the Queue, take only one in your area when you have an area; an issue that lists no files fits every area (Planning). Wherever an issue is listed, never take an epic, which the coordinator plans (Planning), nor an issue labelled blocked, which waits on a peer or the coordinator. An issue with a branch `claude/<issue>` on origin, or a file `docs/agents/claims/<issue>.md` on the default branch, is another worker's, whatever its labels say. An issue GitHub's dependencies say is blocked by an open issue, the blocked-by relation the issue's page shows under Relationships and the issue's dependency summary counts, is not free wherever it is listed and whatever its labels say: it waits until every open issue blocking it is closed, and the board says so beside its title. That relation is neither the label blocker, which marks an issue that stops everyone, nor the label blocked, which a worker puts on its own claim while it waits on a peer or the coordinator; an issue whose summary GitHub does not give is read as blocked by nothing. Before you start, read the board's Overlaps section: open work that changes the same files as the issue you take lands in the order it gives.

## Claim

Push a new branch `claude/<issue number>` from the default branch whose first commit adds `docs/agents/claims/<issue number>.md`: the worker, the plan, the files to touch, the issue's link. Nothing else is in that first commit. The claim branch of issue N is exactly `claude/N`, with N in one to nine ASCII digits and no leading zero, since GitHub refuses only a second push of the same name: `claude/03` is no claim on #3. The board shows such a branch as not a claim, and the push guard refuses a push to one and the protocol check fails a pull request from one, both naming the issue's own claim branch. If the push is refused because the branch exists, another worker has it: delete the local branch and pick another issue.

The claim file takes this shape, with N the issue's number and NAME the worker's name. The board reads two parts of it (sdlc_protocol.claims): the `- Worker:` line (or the older `- Account:`), whose name is the worker's label without the `worker:` prefix (a line with nothing after it but markup or a note in parentheses names nobody: the board shows such a claim as unnamed, since the file is there to be corrected, while the clerk and a release, which must name a worker, take the one the issue's label names, as they do once the pull request has deleted the file), and the list under `## Files to touch`, which fills the board's Files column and its Overlaps until the pull request has files of its own; a release quotes the `## Plan`. A claim file over 1 MB, more than GitHub's contents API gives the text of, is read for none of these: the board names the worker by the issue's worker label, or says the file was not read, and takes no files from it, and a release says where the file is in place of quoting its plan.

```
# Claim: #N

- Issue: https://github.com/OWNER/NAME/issues/N
- Worker: NAME
- Branch: claude/N

## Plan

Two to five sentences: what will change and why, in the order it will land.

## Files to touch

- the paths this work expects to change, one per line
```

## Announce

Add the label claimed and the worker's label to the issue, taking off every other worker's label, one an earlier claim left there or one that gave the issue to several workers, so that from the claim on the labels name the holder alone, as the claim file does; and post the plan as a comment, so the board and the people reading the issue see the same thing the branch says.

## Work in the open

Open a draft pull request at once, from the branch to the default branch, with "Closes #N" in its body. GitHub opens one pull request at a time between the same two branches, so where one that someone who may not write opened from the branch stands in the way, which is no claim's (Rules that hold everywhere), close it, as anyone who may write can, and open your own. Push often: a branch with no commit for 24 hours is released (below). When the board comments "main moved" on the pull request, which it does in whichever run finds the branch behind or conflicting, once per commit of the default branch, the default branch has moved past the branch: bring it in, by rebasing on it and pushing again with `--force-with-lease`, or by merging it in, which needs no forced push and is what a worker in Actions does. The board reads a branch as behind where GitHub calls its pull request behind, as it does under a rule that requires an up-to-date branch, or, where GitHub's word is blocked or draft, which says only that something else stops the merge, a rule still holding the pull request or the draft itself, where the comparison of the branch with the default branch says so. A pull request GitHub calls clean, unstable or has_hooks, a draft among them, since GitHub gives a draft the word its branch has, is not held for being behind under the repository's rules, so it hears nothing however far the default branch has moved; one GitHub calls dirty, in conflict with the default branch, hears it. That `--force-with-lease` is the one forced push the protocol allows, and only on your own claim branch. Since a worker that has fetched holds a remote-tracking ref that matches origin, git itself would take its lease onto any claim, so before a lease onto `claude/N` the push guard reads, in the clone the push runs in, or in each clone it may run in where the guard cannot tell which, the claim file `docs/agents/claims/N.md` on the branch the lease holds against (the commit the lease names, else origin's `claude/N` as the fetch left it) and on the branch pushed, each at its tip or, once the branch has deleted the file, where its history last added it, and refuses a lease that would take another worker's claim: one whose two files name different workers, or whose branch pushed carries none; a claim file git cannot show leaves the lease to GitHub's rules, as the guard leaves everything it cannot read.

## Finish

The pull request deletes its claim file, says "Closes #N", passes the repository's checks and is marked ready; the issue gets the label in-review. The owner merges, or, for a worker whose file says `auto-merge`, GitHub merges once the required check is green; the merge closes the issue, and the next board no longer lists the claim. Delete the branch after the merge if the repository does not do it by itself. An issue closed without a merge loses its branch too: once no open pull request uses `claude/<issue>`, the repository's tidy workflow deletes it. An issue reopened once its claim ended keeps the labels that claim left, claimed, in-review and its worker's, which would hold it out of the Queue and from every worker, and keep a claim branch that still stands, with in-review on, from ever being released; so the coordinator, in the board's run (Release), frees an open issue GitHub says was reopened that carries claimed or in-review, unless an open pull request marked ready from its claim branch finishes it. Where neither `claude/<issue>` nor a branch `released/<issue>-<short sha>` stands, it puts todo on as a release does, then takes off every worker's label, in-review and, last, claimed, so a run that fails partway leaves the issue for the next; where one stands, it takes in-review off alone, since a claim branch is a claim whatever the labels say, which is released once its branch has gone a day without a commit, in the same run where it has, and a released branch beside the label claimed is a release being undone. A released branch stands here only where the issue's latest release comment that counts came after the issue was last closed, as the issue's events date that close, or where its events list the label claimed put on after that close later than any entry the repository's activity lists for `claude/<issue>` at or after it, as a person undoing the release puts claimed back, before the rename or after it, while a claim made since puts its own before its branch is pushed or deleted, an entry in the label's own second reading as the claim's, and a claim the activity does not list reading as an undo, since an empty list is what an undo with no claim between shows: one an earlier claim's release left before the close, a later claim having ended with the close and the label claimed having come through it, or a claim made since the close having ended with its branch gone, undoes nothing, and counting it would leave claimed and the worker's label on an issue with no claim branch, listed nowhere, for good; where the run cannot read the events, the activity or the comments, or cannot tell whether the author of a release comment after the close may write, or the events record no close, the released branch stands, and a later run reads them again. GitHub's state_reason stays reopened while the issue is open, so a later claim on it is freed by these rules too: its draft carrying in-review, a label only a pull request marked ready earns, loses that label, while a draft its author said is finished still waits for review, since no release takes it (Release). It reads the issue again first and frees none that is closed by then, as a merge closes its issue a moment after the merge, and, where it read no branch for the issue, reads the claim branch again and frees nothing once one stands, as a worker that has just claimed the issue has put claimed and its label on; it reads the claim's open pull request again too, and frees nothing once that is marked ready, and reads the claim branch once more just before claimed comes off, leaving claimed on once one stands (sdlc_protocol.coordinator.freeing).

## Blockers

An issue labelled blocker stops everyone: work it stands in the way of waits until it is done. The board lists every open issue labelled blocker under Blockers, claimed or not, and a worker takes one there before the Queue, as Pick says. It is claimed like any other issue, by one worker, and nobody else fixes it in parallel; a second worker that sees it held waits for it, helps on the one pull request by review, or takes other work it does not stand in the way of (Pick).

## Release

A claim whose branch has had no commit for more than 24 hours is released by the coordinator, unless it is finished: an issue labelled in-review, a pull request marked ready, or a draft whose author's latest comment on it starts with "finished; ready to mark" waits for review however long it takes. That comment is how a worker that may not mark its own pull request ready, a cloud session whose gh pr calls are refused, says it is done, for a maintainer to mark. When a branch's last commit came, here and below, is when GitHub received the push that set its head, as the repository's activity records that push, so no worker's clock decides it (sdlc_protocol.adapters.github.head_since); an entry that set the branch to another head, or deleted it, dates it too when it came after the run began, a push after the run read the branch, while an older one is stale and lists no push that set the head; the head's committer date stands in where the activity, read once more after a pause when the first read lists no push that set the head or GitHub gives it no answer that holds, still lists none, or where GitHub refuses to read it, since the push a run was started by is the one the activity is likeliest not to list yet, but never earlier than the newest entry either read listed for the branch, which the push that set the head came no sooner than. In the run that a push to the branch started, which the workflow's event names, a head no read dates is dated at the run's start instead, and so is one a read dates by an entry that set it more than a few minutes before the run began, an older push of the same head that the activity lists while it does not list that push yet, or that push itself where the run, queued behind others, began that much after it, for that run alone, since that push came just before the run, whatever the two reads list, so no claim is released in the run its own push started; the next run reads the activity again. The coordinator is a step of the board's own run (sdlc_protocol.coordinator, through sdlc_protocol.adapters.github.coordinate), on the repository's own token, so releasing needs no Claude account and no routine. Before it releases, it frees each reopened issue whose labels still speak of a claim that ended with its close (Finish), so the in-review that claim left finishes no claim, and a claim branch still standing for the issue is released in that same run once it has gone a day without a commit. The coordinator first takes the label claimed and every worker's label off the issue, a label already gone counting as taken off, and puts the label todo on it when it carries none of todo, epic and blocker, so the Queue lists it again even when a worker's label alone gave it to the worker, while a blocker is listed under Blockers without it; then it posts a comment on the issue whose first line is `<!-- sdlc-coordinator: claim-released -->` and which says why and whose the claim was, what the branch holds beside the default branch and what the claim's plan was, so the next worker can carry the work on or start over. A release counts only once both are done (below). A run that fails at the labels, taking one off or putting todo on, puts back the labels it took off, even one whose taking off GitHub answered with an error, unless GitHub refused it with an answer from 400 to 499 other than a rate limit's, on a try that followed none GitHub refused for a rate limit, which GitHub gives in place of taking it off, since GitHub may have taken it off and a label put back that is still on changes nothing, and takes off the todo it put on, even one whose putting on GitHub answered with an error, since GitHub may have written it, so the issue is as it was and the next run starts the release over. A run whose comment fails reads the issue's comments, and the comment there after all, one GitHub wrote and lost its answer to, makes the release whole. Where they list none and GitHub refused the comment, with an answer from 400 to 499 other than a rate limit's, on a try that followed none GitHub refused for a rate limit, which GitHub gives in place of writing anything, the run puts back the labels it took off and takes off the todo it put on, so the issue is as it was and the next run starts the release over. Where they list none after any other answer to the comment, a rate limit's refusal, a 429 or a 403 that names a rate limit or a wait in retry-after, on the last try or on one the run made the comment again after, which GitHub's documentation never says it gives in place of acting on the call, a server error, a redirect, an answer the run could not read or no answer at all, none of which says GitHub wrote nothing, and GitHub may list a comment it wrote only later, or where the run cannot read them, whatever GitHub answered the comment with, the run cannot tell whether a release comment stands, its own, an earlier run's or one someone else wrote: it leaves the labels as the release left them and counts no release of its own, so its page lists the claim as held and the branch keeps its name, since labels put back beside a comment that stands would hold the claim for good, the comment telling every later coordinator the claim is released and the label claimed telling the board it is held, and the next run, reading the comments, finds the release whole where a release comment that counts stands, or releases the claim again where none does, unless its holder pushed since, which keeps the claim, its labels as the release left them, naming no holder, until it finishes, a person puts them back or it goes a day without a commit and is released again, or a person put the label claimed back beside a comment that stands, which undoes that release (below), though a branch at a head a release already kept is released in that same run by its latest release comment, where one that counts stands, which counts for such a branch whenever it came, with no word on the issue of this run's release where GitHub wrote none. Where GitHub refuses the putting back too the labels are left off with no comment, until a run releases the claim or a person puts them back. It never pushes to the branch, deletes it or renames it. It takes its candidates from the open issues that have a branch `claude/<issue>`, whatever their labels, and skips a claim whose latest release comment came more than 24 hours after the branch's last commit, which is a claim already released; sdlc_protocol.claims.release_due is that rule, so a coordinator that runs on every board run releases each claim once, and releases again one it released too soon or one claimed anew that went idle again. A person or a coordinator routine may release a claim too, in the other order: the comment first, then the labels, todo put on as the coordinator puts it, since taking a label off starts a board run, whose coordinator, finding no release comment yet, would release the claim with a comment of its own; or, for any claim but a draft its author said is finished, a person takes the labels off and leaves the comment to that run.

The board does the rest (sdlc_protocol.board.released_keys). A claim counts as released when its issue is open, labelled neither claimed nor in-review, its pull request, if any, is still a draft, and its latest release comment came more than 24 hours after the branch's last commit, with no commit since. That holds for a draft whose author said it is finished as for any other, though the coordinator never releases one: a person releases one by hand with the release comment first, then the labels, which frees it, the board reading its issue's comments once the label claimed is off. Taking its labels off alone leaves it held, with no labels, until a person posts the release comment or puts the labels back, since no coordinator's comment follows. A release comment counts when it is by the repository's owner, a member of its organization or a collaborator, by the repository's own workflows (the bot `github-actions[bot]`, which only a workflow someone who may write put there can write as), or by anyone else who may write to the repository. The board then leaves the claim and its pull request off the page and lists the issue as it lists any unclaimed one, in the Queue or, for a blocker, under Blockers, though until the same run has renamed the branch Pick reads the branch as another worker's and the clerk deals the issue to nobody (Planning), and renames the branch to `released/<issue>-<short sha of its head>`: the name `claude/<issue>` is free, the work stays under the new name, GitHub closes the branch's pull request with the rename, and the board says on the issue where the branch went. The next worker claims the issue by the steps above, a new branch `claude/<issue>` from the default branch, and may carry the released work on in it after the claim commit, keeping its own claim file. Since the coordinator releases in the board's own run, before the board is rendered, the same run renames the branch. A release comment made sooner, or by anyone else, frees nothing; a commit pushed to the branch before the rename, its holder coming back, keeps the claim; and putting the label claimed back undoes a release, before the rename or after it, when the branch is renamed back and its pull request reopened. A branch pushed again at the head a release already kept, one a branch `released/<issue>-<short sha>` stands at, brings nothing new: its latest release comment counts for it whenever it came, before that push or after (sdlc_protocol.board.release_counts), so the board deletes it instead of renaming it, since its work is already kept, and the coordinator releases it only where the board counts no release of it, no release comment counting or the label claimed put back, once it has gone a day without a commit. Until the board has renamed the branch, a push of the name is still refused; the board renames it in the run that releases the claim, or, for a release made by hand, in the run that the label's removal starts. When GitHub refuses the rename for good, for a ruleset whose target takes in the claim branches or a token without the right, the board says so once on the issue, naming each ruleset that applies to the two names with its rules (sdlc_protocol.board.rename_refused_text), and every run tries the rename again; a ruleset meant for the default branch leaves `claude/**` and `released/**` out of its target.

## Overlaps

Two pieces of open work that change the same file meet when the second lands. The board's Overlaps section lists each file that more than one piece of open work changes, an open pull request by its files or, while it changes nothing but its claim file, by the files its claim lists, and a claim with no pull request yet by the files its claim lists, with that work in the order it should land: a blocker first, since it stops everyone; then work marked ready, which waits only for its merge; then the oldest, the work that began first, when GitHub says the push that made its branch came, or, for a pull request from a fork or from a branch it says nothing of, when the pull request was opened; work whose beginning nothing says, which can only be a claim with no pull request yet, counts as the newest, since a claim opens its draft at once (Work in the open), and the number breaks a tie (sdlc_protocol.board.overlaps). In the same run the coordinator tells each piece of open work about the work it meets, once, in a comment whose first line is `<!-- sdlc-coordinator: overlap <numbers> -->` naming every piece it told of, with the shared files and the order, and tells it again only when work it has not been told of starts to meet it (sdlc_protocol.coordinator.overlap_comments_due); a marker counts only from an author whose release comment would count (Release), so no one else can keep work from being told. The marker names each piece by its identity: a claim and its own pull requests are one piece, the issue's number, told on that issue, so opening a pull request tells nothing again, and a marker on one of the claim's own open pull requests counts as one on the issue; a pull request that is no claim's is a piece of its own, its number, told on itself (sdlc_protocol.board.identity). An issue's number names each claim on it in turn, so a marker tells a claim's work, or tells of it, only when it came no earlier than the push that made that claim's branch, as GitHub dates that push for the order above, and every marker counts for a claim whose push GitHub does not date (sdlc_protocol.coordinator.heard_of). Each piece after the first brings the default branch in once the one before it has landed.

## Planning

An issue labelled epic is a request for more than one piece of work. The coordinator, here Claude, in the repository's coordinator workflow or a coordinator routine, plans it into tasks, each with the files it owns and the interfaces it shares with the others, and gives each task to a registered worker whose area fits, labelling it todo and `worker:<name>`; where no worker is registered the tasks go to the open queue, labelled todo alone. When a worker labels its task blocked, the coordinator settles what it needs; when the last task closes, the coordinator integrates: it checks the default branch as a whole and fixes what the pieces broke together, under this protocol. The clerical part, writing the plan into the epic, opening the tasks and telling each worker what to do next, is code, not Claude: sdlc_protocol.team, run as `python3 -m sdlc_protocol team`. Workers that ask at the same moment, as the workers in Actions of one run do, are dealt the open work so no two race for one claim: each takes its own claim that needs work, one whose claim file names it, whatever the issue's labels say, or, where no claim file names a worker, one whose issue's label names it, a worker:<name> label before the older spellings and the first by name among labels of one spelling, as a release names whose the claim was, but never a claim that counts as released, which no worker carries and none takes until the board has renamed its branch (Pick, Release), nor a claim labelled blocked, whose holder waits on a peer or the coordinator (Labels) and so has nothing else to do; else the task it was given, one given to it alone first, and a task the labels of several workers give going to the first of them with nothing else to do; else the next unclaimed blocker or queued issue, blockers first, whose listed files fit its area (the Task form's "Files likely touched", or a planned task's "Files to touch"; an issue that lists none fits every area). Each of these is taken in Pick's priority order, a worker's own claims, its given tasks and the shared work alike, blockers still before the queued issues: an issue labelled p1 first, then p2, then p3, then one with none of them, the lower number first among equals. The order is the team's: every worker the deal is for, in the workers' workflow every registered worker in Actions, whether or not the run starts it, so a worker outside the run keeps its share, and two runs that look at one state deal no issue to two workers. The workers of one run are dealt from one look at the repository, taken once for the run and handed to each worker (`python3 -m sdlc_protocol team deal`), since two workers looking for themselves at different moments, one while a peer's ready pull request is still clean and one after the default branch has moved past it, could be dealt one issue; a worker that asks alone (`python3 -m sdlc_protocol team next`) is dealt by the same rule from its own look.

A plan may say that one task must close before another can be taken: each task lists, as `depends_on`, the positions of the tasks it depends on, counted from 1 in the order the plan lists them, and the clerk, once every task is open, writes each as GitHub's blocked-by relation on the blocked task, naming the blocker, and says in the plan section which tasks block each task and which relations GitHub refused to record, so the order is in the epic's text even where GitHub did not keep it. A plan whose dependencies do not hold together, a position the plan has no task of, a task that depends on itself, or a cycle, is refused whole before any task is opened. A task an open task blocks is not free until that task is closed (Pick), and the board's Dependencies section draws each open epic's tasks and their blocked-by relations as a flowchart, with the goals above their epics and no relation of an epic's own, and writes the same chart into the epic's body between the markers `<!-- sdlc-board: graph -->` and `<!-- sdlc-board: /graph -->`, beside the plan section, so the epic's own page shows it, touching nothing outside the markers, leaving alone a body whose markers are not one clean pair, and taking the chart out of an issue that owes none any more; a sub-issue or a blocking issue that lives in another repository is drawn nowhere, since its number means nothing here. A node's label is its issue's number, its title folded to ASCII and cut, and its sub-issues' count where it has any; in the title, `#` first and then the percent sign, the dollar sign, the quote, `|`, `<` and `>` are written as Mermaid's entities (`#35;`, `#37;`, `#36;`, `#quot;`, `#124;`, `#lt;`, `#gt;`), so that no title ends its node, opens a Mermaid directive (`%%{`) that restyles or breaks the chart, or opens the math (`$$`) whose typesetting a bad formula stops from drawing it, and a second writer of the same chart writes the same bytes; Mermaid still draws some words of a title its own way, such as `fa:fa-<name>` as an icon. A run whose reads for the section would reach the calls the board keeps in reserve, or one of whose reads GitHub failed, leaves the section out with one line saying so, writes no chart, and draws it on the next run.

## Locks

This section is off unless the switch says otherwise, and nothing above depends on it: the environment's `SYMPHONY_LOCKS`, else the file `.github/symphony-locks`, says off, advise or enforce, and anything else is off (sdlc_protocol.locks.mode_of).

A claim locks an issue; a lock is how a claim says what it works on, so that two claims never edit one function, one section or one resource with no merge at once, the rule a coordinator otherwise applies by hand by naming one owner. A key names what is locked: `path` the whole file; `path#name` one symbol of it, a Python function or class or `Class.method`, read with the standard library's ast from its first decorator to its last line, or a Markdown section by its headings from the top, as `Title > Section`; `path#<top>` everything in the file outside its named symbols; and `scheme:id`, such as `doc:a1cb9900`, a resource outside git, always whole. Any other file is locked whole. Two keys meet when they name one resource and either is the whole of it, or they name one symbol, or one symbol holds the other. A lock is a write or a read: two entries conflict when their keys meet, at least one is a write, and they belong to different claims. A claim's write on a Python symbol comes with reads on what that symbol's code names directly, the file's other symbols, its class's methods through self and names taken from the repository's own modules by a module-level `from ... import` (sdlc_protocol.locks.plan), so a change to what another claim builds on waits; what a reference does not show, a dynamic call or a dependency through data, is the required check's to catch on the merged result.

The locks are entries in one table, LOCKS.json on the branch `locks`, which moves only by fast-forward pushes and is never forced or deleted: a worker reads the table, decides on the tip it read, and pushes one commit on that tip, which git refuses once the tip has moved, so the push is a compare-and-swap, and a refused worker reads again and decides again (sdlc_protocol.adapters.git_locks.change). The compare-and-swap is the clients' alone until a ruleset on `locks` blocks forced pushes and deletions, which the switch needs before enforce: the push guard refuses a forced push anywhere but does not yet refuse deleting `locks`, which would drop every lock. Locks taken at the claim are pushed with the claim branch in one `git push --atomic`, the branch with a lease that expects no branch at all, so a worker gets the issue and every lock it asked for, or nothing, and never adds commits to a claim already there; a claim branch the remote already has means the issue is held, and any other refusal that the table moved. A claim takes locks later only once its branch is on origin, since until then its locks would count as ended. A worker never waits while it holds locks: refused at the claim, it picks other work; refused when it asks for more mid-work, it finishes what it holds and files the rest as an issue of its own that names the holder's. Nobody waiting while holding means no deadlock.

A lock lives while its claim does: the branch `claude/<n>` is on origin and its head is not yet in the default branch, read by the branch and not by a commit, since a worker may rebase its own claim. The board's run also ends the locks of a claim whose issue is closed or whose release it counts, which git alone cannot see. A lock that has ended is dropped, by the board's run or by any worker in the commit that takes its key, and never comes back: a claim whose release is undone takes again what it held, and may be refused. A new claim of the same issue inherits what is left under its number.

Git cannot keep an edit inside its grant, so a check holds each change to the locks (`python3 -m sdlc_protocol locks verify`): the change from the merge base, hunk by hunk on the base version, gives the keys it touches, an insertion at a symbol's edge touching the symbol and `<top>` both, since a three-way merge conflicts on edits that only abut. A touched key that another live claim holds is a problem for any pull request; for a claim's, so is a touched key it holds no write on, except in a file the change adds. At advise the check prints its problems, at enforce it fails on them. The table is trusted to everyone who may write the repository, as the claim branches and the board are.

The same reading tells a change whether it must bring the default branch in (`python3 -m sdlc_protocol locks overlap --base origin/main`), with no lock table and for any pull request, a claim's or not: what the default branch changed since the change's fork from it, with the reads its edited Python symbols take, is set beside what the change edits, with its own reads, and the change brings the default branch in only where the two meet with a write on either side, the default branch having edited what the change edits or builds on, or built on what the change edits. A Python file the change writes whole, or outside its symbols, reads what the whole file depends on, since such an edit builds on whatever the file does. Where they do not meet, the change lands as it is, and what a reference does not show is caught by the default branch's own check after the merge, as the required check on a pull request runs on a test merge made when it last ran and never at the merge itself; a repository that runs it leaves off GitHub's rule that a branch be up to date before it merges, which would ask every change to bring the default branch in whatever it changed. Judged at GitHub's test merge, the checkout a pull_request event gives, it reads the branch's own side, and in a shallow clone it deepens until it finds the fork. It obeys the same switch: at advise it prints the meetings, at enforce it fails on them.

## Policy and worlds

The rules above are the same wherever they run. Two things change from one place to another, and sdlc_protocol.gate names them: a Policy, which says how the protocol behaves, and a World, which is where the branches live and which an adapter implements. The gate's decisions (claim, open a pull request, mark it ready, report its status, draw the board) are functions of the policy, the world and a queue of issues and pull requests, and they run no git and no HTTP themselves.

The policy's fields, with the values this document describes as the defaults:

- claim_prefix, `claude/`: what a claim branch's name starts with, before the issue's number.
- required_check, `check`: the check that must be green on the branch's head before the gate merges; empty where merging cleanly is the whole check.
- bring_main_in, `rebase`: how a branch takes in a default branch that has moved. `rebase` is a session's way, above, with the one `--force-with-lease`; `merge` is a worker in Actions', merging the default branch in so nobody force-pushes. The "main moved" answer says the steps in the policy's own way (sdlc_protocol.gate.main_moved_instruction).
- who_merges, `owner`: who moves the default branch. `owner` is the repository's owner by hand, as above; `gate` is the gate itself, when a pull request is marked ready; `auto-merge` is GitHub, once the required check is green, as a worker whose file says so lands.
- idle_after, 24 hours: how long a claim may go without a commit before it is released.

Two presets name the two ways of landing above: ACCOUNT_POLICY (rebase, the owner merges) and TEAM_POLICY (merge, auto-merge). A policy also carries remote and default_branch, `origin` and `main` unless the place calls them otherwise, which are only the names its answers use, so an instruction reads `origin/main` or `team/main` as the place does.

A world answers six questions: the default branch's commit (main_sha), a branch's commit (branch_sha), how a branch stands to the default branch (standing: clean, behind, conflicting or unknown), the state of the required check on its head (check: green, red, pending or none), the merge itself (merge, which returns the default branch's new commit or raises why not: MainMoved, the default branch left as it was; MergeRefused, for a reason the branch's author fixes; GateFailed, the world could not act), and the time (now). What each adapter supplies:

- sdlc_protocol.adapters.github, a repository on GitHub through the REST API, with a workflow's GITHUB_TOKEN or an App installation token: the standing from the pull request's mergeable_state, told apart further by mergeable and by how far the head is behind its base where GitHub says only that something blocks the merge, and unknown for a branch with no open pull request; the check from the check runs on the branch's head that carry the required check's name; the merge through GitHub's merge API, pinned to the head the gate looked at, and only when who_merges is `gate`, any other policy being refused with NotAllowed; the clock as given, or the wall clock.
- sdlc_protocol.adapters.bare_git, a bare repository that agents share, as coordbench's sdlc arm does: the standing from git itself, in a scratch clone, with the conflicting files named and two more words a git world can tell apart (no branch, nothing new); no checks, so the check is always none; the merge as `git merge --no-ff` under the gate's own committer identity, pushed without force, a conflict or a refused push being MainMoved; the wall clock.
- sdlc_protocol.adapters.memory, a world held in memory for tests and simulations: standings and checks set by hand, a clock that moves only when told, so a simulation can hold a check pending for as long as it means CI to take, and a record of every merge.

A refusal carries the code its command exits with, so a script can tell one kind from another: 1 refused (claim first, push, commit something), 2 someone else's (another holds the claim, the issue or the pull request), 3 main moved (bring the default branch in and try again), 4 gate failed (the world could not act).

## Rules that hold everywhere

- One issue, one branch `claude/<issue>`, one pull request.
- Never push to another worker's branch. Never force-push the default branch or any branch that is not your own claim. The push guard (sdlc_protocol.guard, run as a Claude Code hook through `python3 -m sdlc_protocol guard`) refuses those pushes before they run, and branch protection on GitHub stands behind it.
- Memory rides in the same pull request as the change it came from.
- The repository's checks pass before a pull request is marked ready.
- CI holds a `claude/<issue>` pull request to this protocol (sdlc_protocol.protocol_check, run as `python3 -m sdlc_protocol check`, part of the required check): the claim file is there while the pull request is a draft, gone once it is ready, the body closes its issue, and the branch lives in the repository itself, never in a fork; and a pull request from a branch that reads as a claim and claims nothing, as `claude/03`, fails it.
- No pull request adds or changes a claim file other than its own issue's on its own claim branch. The protocol check reads, in the checkout it runs in, over every path, the branch's own change, from each commit where the head the event names left the event's base (every merge base) to that head, and, where the checkout is GitHub's test merge (a merge whose second parent is the head the event names, whatever its first, since GitHub makes the merge on the base branch as it stands while the event's base is a commit set when the pull request was opened, which the base may have moved past, or a merge of the base and any second where the event names no head), the merge's change against its first parent as well, so that what the base branch did since the branch left it is never read as the pull request's; it fails a pull request either change of which adds or changes `docs/agents/claims/<n>.md` for any issue but its own claim's, a claim stacked on another claim's branch, a pull request from a branch that is no claim's and a copy of a stale claim file the base already holds among them, since a claim file that reached the default branch would read as a claim on that issue there (Pick), and the board and the push guard would read a later claim's branch that brought the default branch in as that file's worker's. It fails one that makes `docs`, `docs/agents` or `docs/agents/claims` anything but a folder, makes a claim file a link or a submodule, adds a path more than one level below the claim folder, or adds a path that is one of those folders, lies in the claim folder or names a claim file but for its letters' case, since a checkout would then show claim files git does not hold. A pull request that deletes a claim file, or any of those, passes, so a stale one can always be taken off the default branch. The check runs git with no GIT_* variable of its environment and fetches from origin the commits it lacks, the base, the head, the commit the test merge was made on and as much history as finding where the head left the base takes; where the folder it runs in holds `.git` and git is missing, refuses the checkout, cannot fetch what it needs or finds no such commit, or the checkout is neither the head the event names nor its test merge, the check fails with the reason, quoting git's last words where it gave any; and where the folder holds no `.git` the check reads no change and judges the head's own claim file alone (sdlc_protocol.protocol_check.stray_claim_files and claim_folder_problems, sdlc_protocol.cli.changed_claims_in).
- A claim and its pull request live in the repository itself, so a pull request from a fork is no claim's, whatever its branch is called: the board lists it as a pull request of its own and tells it what it tells any other, it finishes no claim, marked ready or said finished, and a release's rename, which closes the claim's own pull request, leaves it open (sdlc_protocol.board.claim_of).
- A claim's pull request is opened by the repository's owner, a member of its organization, a collaborator or anyone else who may write to the repository, or by a GitHub App, which opens one only where it is installed, as the workers in Actions open theirs; a pull request anyone else opens from a claim's branch, as GitHub's documentation says anyone who may read the repository can, is no claim's either: the board lists it as a pull request of its own and tells it what it tells any other, it finishes no claim, marked ready or said finished, and a release's rename closes it with the claim's own, since GitHub closes each open pull request whose branch it renames. Where GitHub will not answer whether someone may write, a pull request they opened stays the claim's, and a release comment or an overlap marker they wrote counts for nothing, so a lost answer never frees a finished claim and never keeps work from being told (sdlc_protocol.board.claim_of, sdlc_protocol.claims.is_trusted_author).
